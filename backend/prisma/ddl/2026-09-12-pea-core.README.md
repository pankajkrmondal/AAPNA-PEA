### ⚠️ Run the WHOLE file — press Ctrl+A first

**In pgAdmin, F5 executes only the SELECTED text if anything is highlighted.**
This is the single easiest way to get confusing results here.

```
1. Click once inside the Query editor
2. Ctrl+A        ← selects everything, so F5 cannot run just a fragment
3. F5
```

You should get a **result grid with 7 rows** at the end. If no grid appears,
only part of the file ran.

**Symptom of a fragment run:** `NOTICE: relation "pea_users" already exists`
while the Object Explorer still shows 49 tables. Earlier versions of this file
wrapped everything in `BEGIN … COMMIT`, so a fragment left an **open
transaction** — the tables existed inside that one Query Tool session but were
invisible to every other connection, including the Object Explorer. If you see
this, run `ROLLBACK;` in that tab, then run the whole file.

The explicit transaction has since been removed: every statement is idempotent
and non-destructive, so each auto-commits and a partial run is completed simply
by running the file again.

## 🚨 The one rule that matters

> **NEVER run `prisma migrate`, `prisma db push`, or `prisma db pull` in the PEA project.**

PEA's tables share the `public` schema with the 48 ATS `rpa_` tables, and the
application connects as `appuser` — **which owns those tables**.

Prisma treats `schema.prisma` as the truth for the entire schema. PEA's file
contains 10 `pea_` models; the database contains 58. Prisma reads the 48 ATS
tables as drift:

| Command | What happens |
|---|---|
| `prisma migrate dev` | Generates `DROP TABLE` for all 48 ATS tables. `appuser` owns them, so **the drops succeed**. |
| `prisma db push` | Same, applied immediately with no migration file. |
| `prisma migrate reset` | Drops the entire schema. |
| `prisma db pull` | Non-destructive, but has **no table filter** — imports all 48 ATS models into `schema.prisma`, after which PEA's client can read and write every ATS table. |

### Controls in place

1. **`package.json` has no `migrate` or `push` script** — only `prisma:generate`.
   Nothing to run from muscle memory.
2. **`prisma/schema.prisma` is hand-written** with `pea_` models only. We wrote
   the DDL, so we know the shape; `db pull` is a convenience we forgo.
3. **`prisma/migrations/` is in `.gitignore`** so an accidental migration cannot
   be committed and look sanctioned.
4. **`pg_dump` before every DDL run.**
5. **A restricted `peauser`** — not yet available. See below.

## Why there is no `peauser` yet, and why it now matters more

`00-capability-check.sql` returned:

| Check | Result |
|---|---|
| `is_superuser` | `false` |
| `CAN_CREATE_ROLES` | **`false`** ← cannot create a restricted role |
| `CAN_CREATE_SCHEMA` | `true` |
| `I_OWN_ALL_RPA_TABLES` | **`true`** ← `appuser` owns all 48 ATS tables |
| `max_connections` | `100` (measured usage: 8) |

Because PEA's tables now live in `public` rather than a separate schema, the
`peauser` role is **the only remaining control that would refuse a destructive
Prisma command at the database level**. Everything else on the list above is
process discipline, which works right up until the day it doesn't.

### The ask — two lines, no downtime, no restart

Whoever administers the database server runs:

```sql
CREATE ROLE peauser WITH LOGIN PASSWORD '<generate a strong one>'
  NOSUPERUSER NOCREATEDB NOCREATEROLE;
GRANT CONNECT ON DATABASE recruitmentautomationdb TO peauser;
```

Then **re-run this same DDL file**. Section 12 detects the role and applies
every grant automatically — `appuser` owns the ATS tables, so it can issue the
read-only grants itself with no superuser involvement. The file is idempotent.

Finally, change `DATABASE_URL` from `appuser:` to `peauser:` and restart.
**No application code changes.** `NOCREATEDB` alone stops `prisma migrate dev`,
which cannot create its shadow database without it.

## Three design choices worth knowing

**1. `ats_pipeline_id` has no foreign key.** It is a soft reference to
`rpa_candidate_pipeline.id`. A real FK would couple the two systems' lifecycles
— ATS could not restructure that table without breaking PEA, and an ATS restore
could fail on PEA's constraint. Integrity here is the application's job, by
choice.

**2. `office_email` is unique on `lower(trim(...))`.** The master sheet has
names and addresses with mixed case and trailing spaces (`"Shelly Jain "`,
`"Priyanka Khurana "`), so a plain `UNIQUE` would let duplicates through.

**3. `shadow_mode` ships as `true` on purpose.** The sweep writes
`pea_email_log` rows with `status = 'suppressed'` instead of sending, so PEA's
"would have sent" list can be diffed against what Power Automate actually sent.
Three clean days, then set it `false`. Plan R6, stage 1.
